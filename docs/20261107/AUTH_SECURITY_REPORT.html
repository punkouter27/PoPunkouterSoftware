Security & access control

No logins, one staff key, and nothing personal leaves unmasked

Every visitor is anonymous, on purpose. Reading is open to all. The three actions that change something need a secret key that only the owner's nightly job holds, and the two actions that cost money have a speed limit.

It is a museum with free entry. Anyone can look at the exhibits. The doors marked "staff only" need a key card, and the gift shop lets only so many people through per hour.

The staff key check

Before a staff-only action runs, a guard asks three questions in order. A wrong answer at any point stops the request with a clear message.

Think of it as a visitor badge scanned at the staff door (this app has no JWT; the key header is the badge)
  1. Is the door in use here?If management actions are switched off, answer 403 "disabled in this environment".
  2. Is there a lock?In production, if no key is configured, refuse with 403. The door never opens just because the switch is on.
  3. Does the badge match?Compare the X-Management-Key header with the stored key in constant time. Missing or wrong: 401.
  4. Run the actionOnly now does the scan, cancel or restart happen.

ManagementActionFilter.cs:25-60. Applied to refresh, restart and cancel at DiagEndpoints.cs:87, DiagEndpoints.cs:126, DiagEndpoints.cs:135. Switch default: on in Development and Testing, otherwise read from config; it is true at appsettings.json:40.

if (!string.IsNullOrWhiteSpace(adminKey))
{
    var presented = http.Request.Headers["X-Management-Key"].ToString();
    if (string.IsNullOrEmpty(presented) ||
        !CryptographicOperations.FixedTimeEquals(
            Encoding.UTF8.GetBytes(presented), Encoding.UTF8.GetBytes(adminKey)))

Secrets: where they live and how the app reaches them

Passwords and keys are kept in a locked cabinet in Azure (Key Vault). The website opens it at startup with its own Azure identity, so no secret is typed into code or settings files.

Shared vault

kv-poshared2, shared by every Po app. Secrets named PoPunkouterSoftware--Section--Key lose the prefix and become settings.

Managed identity

In Azure, the site's system-assigned identity reads the vault through a classic access policy. Locally, your az login does.

Tests never touch it

The Testing environment skips the vault entirely, so a test run cannot read or leak a real secret.

No user-secrets

Per-machine secret files were removed; a value only one machine has looks like a bug everywhere else.

Keeping personal and estate data private

Email addresses

Masked on the server before they leave: first two letters, stars, last letter, full domain. Display names that look like emails are masked too.

Subscription id

Rewritten to /subscriptions/**** across the whole JSON of the report, so a field added later cannot slip past.

Exceptions

Only exception types are stored with the scan, never messages, because messages can contain user data.

The report file

Kept in App_Data, outside the public web folder. It once sat where anyone could download it.

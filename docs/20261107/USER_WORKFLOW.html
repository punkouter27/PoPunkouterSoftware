User journeys · what people do here

Six journeys, from browsing to a 3 a.m. phone alert

Each journey starts with what a person wants, then shows the steps the app takes for them. Switch to Standard for the flowcharts, or Deep-dive for the exact code.

1 · A visitor browses the app catalog

A visitor opens the home page and sees every app in one table. If the saved report is more than 12 hours old, the site quietly starts a fresh scan in the background while showing what it already has.

  1. Open /The page asks the website for the portfolio list.
  2. The list comes from a fileThe catalog file apps.json decides which apps exist. Live Azure data only adds decoration, so a failed check never hides an app.
  3. Old report? Refresh itIf the last scan is older than 12 hours, a background rescan starts, at most once every 30 minutes.
  4. Read the tableEach row shows the picture, description, sign-in method, tech stack and AI services. Hover or tap any value for an explanation.

2 · The owner checks fleet health

The owner opens /azure and reads, top to bottom: how things are, what to do, what it costs, and the uptime evidence. The first screen loads one small summary so it is fast; the full report loads only if they open Advanced diagnostics.

  1. Open /azureThe page loads settings and a compact summary.
  2. Read the statusTwo AI-written sentences, three tiles (health, cost, projection) and what changed since the last scan.
  3. Act on "Needs attention"Plain sentences such as "an app is down" or "a certificate expires soon".
  4. Dig deeper, if neededAdvanced diagnostics opens a drawer and fetches the full report, which replaces the list with a ranked queue.

3 · The owner starts a rescan

Pressing Rescan is like asking the building manager to do the night walk right now. The website says "on it" immediately, then sends live progress while the walk takes about 30 seconds.

  1. Press RescanThe button exists only where management actions are allowed; production visitors never see it.
  2. "Accepted" right awayThe website answers at once and starts the scan in the background. A scan already running is joined, not refused.
  3. Live progressProgress messages stream over a live connection. If that connection is down, the page polls and shows an indeterminate bar.
  4. Save and compareThe new report is saved; crossings (certificate, budget, broken page, domain) send phone alerts.
  5. Page updatesWhen the summary says the scan is finished, the page redraws once with the new facts.

4 · Someone asks "who is using my apps?"

The /users page asks the shared app logs, live, who signed in across every Po app. Email addresses arrive already partly hidden, so the page can say "someone at a company tried it" without showing who.

  1. Pick a windowUp to 90 days, because that is how long the logs are kept. The last choice is remembered.
  2. One live queryThis is the only page load that asks Azure something live, with a 20-second budget.
  3. Group by emailThe same person signing in to two apps counts once.
  4. Mask before sendingalexandra@example.com becomes al******a@example.com on the server, before anything leaves it.

5 · The owner's phone buzzes

A small checker knocks on every app's door every 10 minutes. Two missed knocks in a row means "down", and the owner gets a push notification that opens the dashboard on that app's row.

  1. Knock every 10 minutesA plain request to each app. A slow answer (a sleeping free-tier app) counts as nothing, not as down.
  2. Two misses in a rowOnly a change of state sends an alert, never the same state twice.
  3. Push through ntfyOne message to the owner's ntfy topic, which acts as the password.
  4. Tap to see itThe link opens /azure?focus=<app>, which scrolls to and highlights the row.

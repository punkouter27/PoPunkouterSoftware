Overview · what this app is

A control room for one person's fleet of small Azure apps

PoPunkouterSoftware is a website that keeps watch over about nineteen small apps and games its owner runs. It shows which apps are up, what they cost, what needs fixing, and who has signed in to them.

Imagine a building manager with nineteen shops. Every night they walk the halls, write down which lights are off and what the electric bill is, and pin the notes to one board. This app is that board, plus the night walk that fills it in.

Who it is for

The owner

Checks health and spend on /azure, starts a rescan, restarts a broken app, and gets phone alerts when something goes down.

Visitors

Browse the app catalog on / to see what each app is and what it is built with. Nobody logs in; every visitor is anonymous.

Robots

A nightly GitHub Actions job asks for a fresh scan. GitHub READMEs embed an uptime badge. Neither one opens a page.

The four pages

The site has exactly four pages, and that number is a deliberate limit. Everything else is a back-office service the pages call.

Major features

Nightly health walk

One scan visits every app, checks it answers, reads its bill, its certificates and its error count, and saves a report.

One list of what to fix

The scan's findings become plain sentences, ranked so the most urgent problem is first.

Uptime grid

A small background checker knocks on every app every 10 minutes, so each day gets a green, amber or red square.

Spend forecast

Month-to-date spend, a projection to month end, and a warning when one resource group suddenly costs much more than usual.

Phone alerts

A push notification arrives when an app goes down, comes back, or a certificate or budget line is crossed.

Sign-in roster

A live list of who signed in to any Po app, with email addresses partly hidden.

Architecture · how it is built

One website, one saved report, one nightly walk

The whole system is a single ASP.NET Core website that also serves its own browser app. It reads one saved report to draw every page and refreshes that report with a scan.

Think of a shop with a front desk (the API), a filing cabinet in the back (Table Storage), and an inspector who walks the estate and files a new report (the scan). Customers only ever talk to the front desk.

Three rules that shape everything

The report is the spine

Pages show projections of a stored scan. Only one page load asks Azure anything live: the sign-in roster.

Degrading is designed

No storage? Use a local file. No AI? Use a sentence template. A probe failed? Keep the app on the list.

Small first paint

/azure loads a compact summary first. The full report waits until someone asks for it.

Standard · C4 level 2 (containers)

What runs where

  1. One hostThe API serves the browser app's files and its JSON from the same address, so there is no cross-site traffic to allow.
  2. Secrets onceAt startup the host reads its settings from the shared Key Vault using its own Azure identity. No password is stored in the code.
  3. Scan writes, pages readThe scan talks to Azure and public APIs; page loads read Table Storage.
  4. Robots helpGitHub Actions starts the nightly scan and uploads app screenshots, because the free-tier host sleeps and cannot run a browser.
Standard · C4 level 3 (components in the API)

Inside the website

The API is split into four "counters" (slices), each serving one kind of request, plus a back office of shared tools. Counters never call each other; shared logic lives in the back office.

The checkpoint line every request walks

Every request passes the same stations in the same order, like a parcel on an assembly line. Each station can stamp it, stop it, or wave it through.

Think of it as a security checkpoint and assembly line (middleware)
  1. Catch crashesAny unexpected error becomes a tidy problem response, not a stack trace.
  2. Security stickersEvery response gets the content-security policy and anti-framing headers.
  3. Build stampAn X-Commit header says which build answered.
  4. Friendly 404Unknown pages re-run as the app's own not-found page with a real 404.
  5. HTTPS pinProduction only: browsers are told to always use HTTPS.
  6. Request logOne log line per request, at a calm level.
  7. Hang-up handlerA visitor who leaves mid-request is logged as 499, not as an error.
  8. Static filesImages, scripts and the WebAssembly bundle.
  9. Squeeze JSONCompression for JSON only, so pre-compressed files are not double-packed.
  10. Form guardAntiforgery checks.
  11. Who are youAuthentication. In production there is no scheme at all.
  12. Are you allowedAuthorization policies.
  13. Not too fastRate limits on the two endpoints that cost money per call.

AI & external services · who we call, and what happens when they don't answer

One AI model, sixteen outside helpers, and a fallback for each

The app uses exactly one AI model, to write two short sentences about the fleet. Everything else it calls is a plain data service. Every one of them can fail without breaking a page.

The AI is a ghostwriter who drafts the opening line of the daily memo. If the ghostwriter is out sick, a fill-in-the-blanks template writes it instead, and the rest of the memo is unchanged.

The AI status narrator

What it does

Reads the scan's facts and writes at most two sentences (under 40 words) that do not repeat the numbers already shown in the tiles.

When it runs

Once per scan, saved with the report. A "Rewrite this" button asks again on demand. If the facts did not change, the saved text is reused.

What it costs

The cheapest deployment on the shared AI account, at most 900 output tokens per call, and at most 20 on-demand rewrites per hour for the whole site.

What it never sees

Only scan facts. Exception messages are never stored (only exception types), so no user data reaches the prompt.

Before a staff-only action runs, a guard asks three questions in order. A wrong answer at any point stops the request with a clear message.

Secrets: where they live and how the app reaches them

Passwords and keys are kept in a locked cabinet in Azure (Key Vault). The website opens it at startup with its own Azure identity, so no secret is typed into code or settings files.

Shared vault

kv-poshared2, shared by every Po app. Secrets named PoPunkouterSoftware--Section--Key lose the prefix and become settings.

Managed identity

In Azure, the site's system-assigned identity reads the vault through a classic access policy. Locally, your az login does.

Tests never touch it

The Testing environment skips the vault entirely, so a test run cannot read or leak a real secret.

No user-secrets

Per-machine secret files were removed; a value only one machine has looks like a bug everywhere else.
